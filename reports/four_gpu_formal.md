# P1–P6 four-GPU formal campaign (2026-10-20)

User authorization: accept the previous P0 baseline and start at P1; retain training parameters and miniF2F evaluation, use nohup, and change vLLM GPU memory utilization from 0.65 to 0.85. The earlier instruction authorizing formal restarts without repeating all smoke experiments remains in effect. No new P0 receipt or smoke PASS is fabricated.

Preparation uses GPUs 0–3 independently for P1 GPTQ, P2 AWQ, P3 ReasoningQAT block training, and P5 EfficientQAT. P4 and P6 become eligible only after P3 preparation and export pass; both use the same immutable P3 native checkpoint. One method occupies one GPU. Shared token/mask budgets use an exclusive file lock for first publication and comparisons.

After all six preparations pass, GPU 3 runs one pinned retrieval service and GPUs 0–2 each evaluate one method. The next method takes a GPU when its predecessor finishes. Evaluation clients cannot start or stop the shared service. The controller owns service shutdown and refuses to overwrite partial batches. Existing single-GPU campaign and pipeline locks are held for the campaign lifetime.

miniF2F remains the same fixed 244-problem test set, with the same seed, sampling/search budgets, Lean verifier, model export representation, and training hyperparameters. vLLM utilization is 0.85; max model length 8192, max sequences 64, max batched tokens 8192 remain unchanged. Engine profile and its new frozen protocol hash participate in the batch fingerprint. This is an explicitly changed engineering runtime profile relative to historical P0; do not compare wall-clock timings as if hardware and memory allocation were identical.

Pinned Lean workspaces and the Lean 4.16 toolchain are copied to node-local /tmp storage. Every copied file is SHA-256 compared with its source and recorded in a copy manifest. Lake dependency Git metadata must be retained to prevent automatic package re-cloning. Broken, non-runtime toolchain symlinks are recorded and skipped. The local Lean paths and actual lean/lake executable hashes participate in the experiment fingerprint. The controller inherits PATH with the local toolchain first; verifier calls use REALPROVER_LEAN_BIN. No proof/search limits are relaxed.

Separating retrieval removes both GPU memory and compute contention. More vLLM memory can increase KV capacity, but it cannot fix Lean CPU/file-loading stalls, and a larger cache alone does not improve a search that is waiting on Lean. Keep logs of cache blocks, token throughput, preemptions and Lean response timings before attributing a speedup to KV cache.

Validation: scheduler tests exercise real scheduling logic with simulated child processes; shared retrieval ownership and the existing transport, timeout, receipt and gate tests remain required. Targeted live checks cover the local Lean session, valid/sorry proof verification, vLLM initialization and 64-candidate generation at utilization 0.85, and three simultaneous clients receiving matching retrieval results. These checks are infrastructure validation, not full smoke experiments or accuracy measurements.

Runtime evidence is stored in runs/four_gpu_preparation_20261020. Campaign control state is under the chosen results directory/control/status.json; method logs are formal/P*/prepare.log and evaluate.log. Preparation manifests bind artifact hashes before evaluation; final PASS receipts retain all original checks and the full denominator.

Only this stress probe suppresses EOS to force the full decode length; formal sampling is unchanged. Three simultaneous retrieval clients returned identical top-10 results in 8.62–11.92 seconds including cold first-query work. Historical P0 at 0.65 reported 36.03 GiB KV cache / 42,170 GPU blocks, capacity for 82.36 maximum-length sequences versus the configured cap of 64, with no matching preemption messages found. Consequently, existing evidence does not identify KV exhaustion as the main historical bottleneck.
