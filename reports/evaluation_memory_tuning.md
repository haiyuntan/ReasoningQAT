## 显存如何分配

原 P0 真实日志显示 vLLM 0.6.6 使用 `gpu_memory_utilization=0.75`，按可见 79.25 GiB 计算，其预算为 59.44 GiB：BF16 权重 14.24 GiB、非 Torch 0.14 GiB、激活峰值 1.44 GiB，剩余 43.61 GiB 用作 KV cache。CUDA Graph 另有开销。检索进程常驻约 14300 MiB，独立于 prover 的预算。23 GB 的瞬时观测不能代表整个原生评测阶段的峰值。

该模型有 28 层、4 个 KV heads、head dimension 128，BF16 KV 的理论每 token 大小约为 `2 × 28 × 4 × 128 × 2 = 57344 bytes`。8192 token 的单条完整序列约 448 MiB；同请求候选可能共享提示前缀，因此真实分配需按引擎块管理实测。预分配更多 KV cache 不会自动增加有效计算。

当前 BatchMainService 每 GPU 一个评测工作进程，逐题搜索；每个状态同步调用一次 `generate([prompt], n=...)`。冒烟 n=4，正式 n=64。`max_num_seqs` 是调度上限，不是每题额外候选数；增大它不会自行提交多题并发。提高 n 会改变搜索预算，不属于纯调度优化。并发 Lean 搜索需要另外设计共享引擎和独立状态管理，本轮不改搜索算法。

## 压测方法与边界

入口为 `research/scripts/stress_evaluation.py`，使用单 GPU 流水线锁，三个配置串行、各自独立进程，检索保持常驻。原始日志与 JSON 位于 `runs/realprover_eval_stress_v1/`。使用真实完整 BF16 模型和 vLLM，但输入 token 是合成负载，不是证明正确率测试：

- 1024 token 输入，n=4，模拟冒烟并发形状。
- 1024 token 输入，n=64，模拟正式并发形状。
- 7936 token 输入，n=64，输出 256 token，覆盖 8192 上下文上限。
- 32 个 4096 token 请求，每请求 n=4，模拟共享引擎饱和负载。

每个输出强制 256 token，避免 EOS 提前结束使负载过轻。记录加载耗时、输出 token/s、整卡显存峰值和 GPU 利用率；显存包含检索与 prover。每档每负载一次，吞吐是初步测量，不是统计显著的性能比较；合成负载通过也不能保证任意实际输入绝不 OOM。正式搜索预算和门禁保持原样。
